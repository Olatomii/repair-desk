# Repair Desk bug audit

Audit began 2026-09-20 and resumed 2026-09-22. Baseline: `025bf007af7ef180cc7612caff920e6b6778d5c9` on `main`. Dedicated branch: `audit/bug-fixes-2026-09-20`. MEDAGENT was not modified. Scope is correctness, security, existing workflows, deployment reliability, and regression coverage; no cancellation/dispute product workflows were added.

## Findings and fixes

Severity describes the plausible impact within this application, not a claim that an exploit occurred in production. No critical vulnerability was confirmed.

| Finding | Severity | Reproduction / root cause | Fix | Verification |
|---|---|---|---|---|
| Stale approval could approve a different, revised price | High | An old approval request only checked `QUOTED`; reject/requote returned the booking to the same state. Regression failed on baseline. | Every workflow action requires the rendered `expectedUpdatedAt`; conditional updates advance it monotonically. | Baseline/fixed unit comparison; authenticated reject/requote/stale-approval test. |
| Concurrent assignments silently overwrite each other | High | Assignment allowed either REQUESTED or ASSIGNED in its update predicate, independently of the state read. | Exact state and timestamp comparison; a losing request receives 409 without an event or notification. | Baseline/fixed comparison; two simultaneous PostgreSQL-backed requests produce one 200 and one 409. |
| Active profile could belong to a demoted non-artisan | Medium | Eligibility checked profile status but not the user's current role. | Assignment and operator eligibility queries also require ARTISAN role. | Query regression asserting role, active status, city, and service filters; authenticated eligible assignment. |
| Notifications could fail after a successful state change or target a subsequently reassigned artisan | Medium | Route created notifications after the workflow transaction committed and re-read the current assignment. | Notification creation now belongs to the same transaction as state and event changes. | Workflow transaction tests and authenticated lifecycle. Database failure injection was not performed. |
| Retrying a booking request created duplicate bookings | Medium | No server-side request identity. | Required UUID idempotency key, scoped to the authenticated client; duplicate keys return the original booking, different payloads return 409. | Concurrent real-database retries create one booking and return the same ID. |
| Tiny positive quotes could persist as zero; excessive fractional precision was silently rounded | Medium | Positive JS number accepted for a Decimal(12,2) column. | Minimum 0.01 and exact cent precision, keeping the existing upper limit. | Invalid amount matrix; authenticated 0.001 quote rejected. |
| Rejected quote amount/note/date remained on the active booking | Medium | Rejection changed status and approval flags only. | Clear current quote fields; retain rejection timestamp and audit event. | Baseline/fixed comparison and real-database rejection assertion. |
| Successful evidence upload crashed before refreshing | Medium | React `event.currentTarget` was used after awaiting the request. | Capture the form synchronously, then reset and refresh after success. | Real browser upload, refreshed evidence list, authenticated download. |
| Upload authorization could become stale during body parsing | High | Booking assignment/status was read before parsing, then evidence was inserted without rechecking concurrency. | Conditional booking write inside the evidence transaction rejects an intervening lifecycle/assignment change. | Route regression simulates a lost race and verifies no evidence insert. |
| Suspended artisans could still add evidence | Medium | Upload checked assignment but not profile status. | Require ACTIVE artisan profile for uploads. | Authorization code inspection; existing role/ownership route regression coverage. |
| MIME metadata alone admitted disguised content | Medium | User-supplied MIME string was the entire content check. | Check JPG/PNG/WebP/PDF signatures; sandbox downloads and disable private-document caching. | Four spoofed-MIME unit cases, WebP container check, browser upload/download header assertions. This is not malware scanning or a complete file decoder. |
| Request size limits ran only after parsing the complete body | High | Multipart parser could allocate a large attacker-supplied body before checking the file size. JSON was also unbounded. | Bound streamed JSON and multipart bodies, including requests without Content-Length. | Stream-limit regression and normal authenticated multipart upload. No production load/DoS test was run. |
| Malformed JSON/multipart caused unhandled errors | Medium | Parsing errors bypassed input validation. | Convert malformed input into non-sensitive 400 responses. | Both JSON APIs tested with truncated JSON; upload parser guarded. |
| Non-auth mutation routes lacked an explicit origin check | Hardening | Better Auth's origin middleware protects its own routes, not application routes. SameSite cookies already mitigate many cross-site attacks. | Shared exact-origin and Fetch Metadata rejection for application mutations. | Hostile-origin multipart request returns 403; unit origin check. No exploitable CSRF bypass was established. |
| Production origin configuration could fall back to localhost | Medium | Missing BETTER_AUTH_URL silently selected localhost; production also explicitly trusted localhost. | Use Render's canonical external URL fallback, normalize the configured origin, fail on absent production URL, and trust only that origin. | Configuration tests; live baseline login returned invalid credentials rather than invalid origin. |
| Network/proxy failures left controls stuck or falsely implied success | Medium | Fetch/JSON/auth client exceptions bypassed loading reset; notification/logout responses were not checked. | Catch errors, restore controls in finally, and display failures. | Authenticated normal paths; registration network-failure and notification-failure browser regressions. Not every component was separately fault-injected. |
| Repairs after the first 20 were unreachable | Medium | Dashboards used `take: 20` without navigation. | Bounded paging with stable ordering for existing client, artisan, and assignment lists. | Browser creates 23 client repairs, opens page two, and finds the original repair. |
| Artisans could not see home-visit address or preferred date | Medium | Data was stored but omitted from operational views. | Display existing address/date in artisan and operator booking cards. | Artisan address assertion and mobile layout check. |
| Health endpoint stayed green when the database failed | Medium | It returned a constant success without accessing PostgreSQL. | Bounded database query; 503 without connection details on failure. | Success/failure unit tests; real health endpoint in Playwright. |
| Seed reactivated a deliberately disabled city | Medium | City upsert's update branch forced `isActive: true`. | Preserve activation state on updates. | Disabled the local launch city, ran the seed twice, verified it stayed disabled, then restored its original state. |
| Every Render wake/restart pushed schema and seeded data | Medium | Startup combined schema mutation, seed, and web serving. | Blueprint starts only the web process; explicit initialization and controlled migration guidance in DEPLOYMENT.md. | Configuration inspection; no schema changes are required by this patch. Effective Render settings must be verified after deployment. |
| Dependency installation was not reproducible and contained known advisories | High advisory severity | No lockfile; four high-severity package entries reported through Prisma's transitive dependencies. No application exploit was reproduced. | Lock dependencies, use npm ci in CI/Blueprint, pin patched deepmerge-ts and mysql2 through overrides. | npm audit reported zero known vulnerabilities; Prisma generation, seed, typecheck, build, and application tests exercise compatibility. |
| Docker build context could embed local secrets and host build artifacts | High | `COPY . .` had no `.dockerignore`, so a developer's local `.env` and dependencies could enter the image. A clean build also lacked required configuration. | Exclude secrets/generated/host artifacts; use npm ci and build-only placeholder configuration, with real credentials supplied only at runtime. | Dockerfile/context inspection only. Container build was not run because the local Docker engine was unavailable. |

## Coverage and evidence

Local verification completed on 2026-09-22: Prisma generation passed; lint passed with one pre-existing warning; TypeScript passed; **58 unit/API tests passed**; production build passed; **5 Playwright tests passed against the production build**; `npm audit` reported **0 known vulnerabilities**. GitHub CI and live rollout are separate gates and are recorded in the PR/final delivery report.

- Re-read the current main branch, every application API route, role-protected pages, workflow services, Prisma schema, seed, auth configuration, CI and Render configuration.
- Unit/route regressions cover anonymous access to all application API boundaries; role/action denials; owner/assigned-artisan restrictions; malformed JSON; arbitrary-status attempts; evidence ID manipulation; stale evidence writes; notification ownership; quote precision; origin configuration; and database readiness.
- Authenticated Playwright coverage uses real PostgreSQL and independent sessions: client registration, session persistence, artisan/operator sign-in, request creation, assignment conflicts, quote rejection/revision/approval, work lifecycle, evidence, handover conflicts, notifications, sign-out, protected redirects, retry deduplication, and access to older repairs. Test fixtures refuse non-loopback app/database hosts.
- Production-mode browser testing retains Better Auth's production rate limiting. Signup assertions respect its retry interval instead of accepting a 429 as proof of password validation or role protection.
- Manually inspected the live landing/login pages and verified invalid credentials from the actual production origin. Manually registered a synthetic local client and submitted a booking at mobile width; examined the dashboard visually. Artisan/operator checks also exist in the browser suite. Not every privileged flow was manually replayed against the live deployment.
- Render logs show historical invalid-origin errors on September 20 before the deployed origin fix. The inspected live deployment matched the audited baseline. The connector's read-only production SQL query failed with TLS/connection errors, so deployed schema/data integrity was not certified.
- Scanned all 42 baseline Git commits for selected high-confidence private-key/token patterns: no matches. Only `.env.example` was tracked. This is a bounded heuristic scan, not proof that no secret ever appeared in history.
- Existing schema has foreign keys, appropriate ownership/query indexes, decimal amounts, restrictive deletion for clients with bookings, cascading event/evidence deletion with bookings, and session/account cleanup with users. No schema mutation was introduced.

## Remaining limitations and deployment concerns

1. **Database lifetime:** Render reports `repair-desk-db` expires on **2026-10-19**. Its free tier has no managed backups. Resolve persistence and backups before relying on the demo long term. [Render limitations](https://render.com/docs/free).
2. **Deployment settings:** A Blueprint change does not prove a dashboard override changed. Verify the effective start command is `npm start` and build uses `npm ci`. Do not claim automatic schema changes have stopped until that is confirmed.
3. **Migration history:** The repository still needs an explicitly verified baseline and reviewed production migrations. The audit deliberately does not invent or mark a baseline applied against an inaccessible production database. No destructive database operation was performed.
4. **Abuse/storage:** File size and body limits do not impose cumulative user/booking storage quotas or application-wide booking/upload rate limits. Binary evidence is stored in PostgreSQL; repeated valid uploads can consume capacity. Signatures and sandboxing do not certify document safety.
5. **Cancellation/disputes:** CANCELLED and DISPUTED are schema states, but there are no supported mutation/UI flows implementing them. These remain product limitations, not functionality added by this bug audit. Arbitrary status mutation is rejected.
6. **Auth operations:** Recovery/email verification, multi-instance rate-limit storage, and a complete production proxy/IP spoofing assessment remain outside the verified flows. Secret values were not retrieved or printed. Existing in-memory auth rate limits were observed in production-mode tests.
7. **Operational views:** The operator view remains an assignment queue, not an all-stage repair management product. Notifications link to role dashboards rather than a booking detail page. The existing account header still shows public sign-in/register links after authentication; logout remains available through notifications.
8. **Testing limits:** No production load test, malware scanner, exhaustive browser/device matrix, production backup restore, full production database inspection, or Docker image build. Local Playwright uses installed Chrome because the Chromium CDN lookup failed; CI uses Playwright Chromium. An existing PostCSS lint warning remains; lint has no errors.

## Portfolio assessment

The repaired happy path is suitable for a controlled portfolio demonstration once the reviewed changes pass CI and deploy successfully. It should not be represented as production-ready for unrestricted public repair operations. A dependable public portfolio link additionally requires persistent database hosting, verified effective startup settings, and an honest description of cancellation/dispute and operational limitations.
